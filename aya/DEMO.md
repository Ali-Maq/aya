# AYA feature migration demo

AYA brings a specific capability from existing software into a GitHub repository. Its output is a pull request with executable tests, reference evidence, and an exact link between the tested module and the deployed version. The first customer is a developer platform team that wants useful examples from another ecosystem to work on its own infrastructure.

## The Fireworks to Crusoe example

The user requests a repository analyst inspired by Fireworks' SQL tool workflow. AYA ports schema inspection and query execution into Crusoe's Developer Hub fork. A real Crusoe model selects SQL over a fresh snapshot of six public GitHub repositories. The delivered module returns the actual result table and denies writes.

The reference is [Fireworks' SQL tools at a pinned commit](https://github.com/fw-ai/cookbook/blob/6ada4081cf7bdb5cec7dcf066dd29d784f55b232/training/case-studies/agentic_rl_text2sql/sql_tools.py). The original case study includes reinforcement learning and embeddings; this feature ports its SQL interaction pattern. REA executes selected unchanged upstream functions in an isolated process capture. This is source and behavior analysis. The earlier jq example demonstrates native binary decompilation separately.

The concrete opportunity is a missing standalone cookbook. [Crusoe's Cookbooks index](https://github.com/crusoecloud/crusoe-developer-hub/tree/main/examples/cookbooks) describes that section as planned content. Crusoe already has other substantial examples and integrations. AYA can help extend those resources; claiming that Crusoe has no examples would misrepresent the platform.

## Show the product in three minutes

1. **First 30 seconds:** Open [AYA in Onyx](http://localhost:3021/app/factory). Show the three inputs: target repository, desired feature, reference. The preset creates a real GitHub issue with a reviewed contract.
2. **Next 45 seconds:** Show the completed build's investigation, tests, native Hermes sessions, and actual failure or repair history. A fresh run may take several minutes; identify a completed run as a completed run.
3. **Next 45 seconds:** Open the generated pull request and its GitHub Actions result. Show the module, agent-written tests, independent evaluation receipt, and upstream attribution.
4. **Final minute:** Ask “Which three repositories have the most stars?” Change the question to grouping stars by owner. Show the fresh result rows, SQL, source links, Crusoe response IDs, and deployed commit.

An optional second example opens the existing JSON recipe product and downloads a CSV generated by the component recovered from jq. This proves that Onyx is the factory interface while each request selects a different target product.

## What the architecture establishes

The controller freezes the GitHub issue, target commit, and contract digest. It calls Crusoe for a plan, then starts native Hermes in the installed OpenShell worker. Hermes investigates with REA, writes the module and tests, and delegates a focused edge-case review. The controller compares the candidate against independently generated expectations, returns development counterexamples for up to two repairs, and evaluates a fresh random seed before delivery.

GitHub credentials remain in the controller. Candidate evaluation has no network, host files, or credentials. The generated module runs in a fresh restricted Docker container; the model calls the controlled executor through a narrow tool interface. Agent tests also execute without network access. GitHub CI must pass for the exact delivered commit before local activation. New or changed requirements remain proposals until their contract and evaluator are reviewed.

The SQL gate covers ordering, aggregates, empty data, nulls, zero, Unicode, quoted strings, malformed records, writes, multiple statements, recursive queries, and result limits. Four live Crusoe questions are compared with independently computed SQLite results. This checks the complete provider-to-tool path in addition to the module itself.

## The difference from a coding assistant

Coding assistants can inspect references, write tests, use isolated environments, and repair failures. AYA's claim is the reproducible delivery protocol around that work: reference identity, independent acceptance criteria, restricted target paths, bounded retries, preserved failures, CI, and deployment bound to the tested source hash.

The useful experiment is to compare the same feature tasks and model budget with and without these gates. Measure held-out correctness, integration defects, latency, and cost. Do not claim another assistant always takes shortcuts or that AYA is superior without running that comparison. The existing jq run supplies a smaller factual result: an agent-written candidate passed its own development work but failed three independent cases, then repaired them.

## REA capability coverage

The installed server advertises 207 tools. AYA currently exercises native function decompilation and process capture. REA also exposes JavaScript and Electron analysis, APK and .NET inspection, runtime traces, artifact comparisons, static/runtime correlation, reconstruction obligations, and residual unknowns. A listed tool is not proof that every provider is installed or usable here.

The next useful expansion is an obligation ledger for each feature: observed behavior, candidate behavior, comparison result, unresolved difference. For a packaged desktop application, static call paths and runtime traces can establish where the behavior comes from. For source-based API cookbooks, running the reference and testing observable semantics is more relevant than forcing a decompilation step. [REA project](https://github.com/morluto/rea).

## Fine tuning and self improvement

Crusoe documents supervised LoRA training at `https://api.intelligence.crusoecloud.com/v1`, separate from the inference endpoint used by AYA. The workflow uploads JSONL or Parquet data, creates a fine-tuning job, observes validation loss, and retrieves adapter checkpoints. It requires an Intelligence API key and a supported trainable base model. This is not a direct replacement for Fireworks' GRPO training API. No training job is part of this demo. [Crusoe fine-tuning guide](https://docs.crusoecloud.com/serverless-fine-tuning/fine-tune-a-model/).

[Sakana MASS](https://github.com/SakanaAI/mass) combines workflow improvement with parameter updates. AYA currently demonstrates fixed-weight task repair and bounded native delegation. A credible MASS-inspired extension would compare investigation and review strategies on held-out feature tasks, retain successful trajectories, train a supported model separately, and test it against an unchanged benchmark. A second agent or a repaired module alone does not establish recursive self-improvement.

## The You.com follow-up

[You.com's examples](https://you.com/docs/examples) already include research and other practical workflows. [Perplexity's cookbook](https://github.com/perplexityai/api-cookbook) offers a useful source of reference applications. A good second port is a cited research brief on You.com with independent checks for valid source links, quoted evidence, and unsupported claims. This needs working You.com credentials and API-specific contract tests.

On October 17, 2026, GitHub reported 228 stars for Fireworks' cookbook, 202 for Perplexity's cookbook, and 92 for You.com's agent skills repository. These are repository interest signals, not ratings of individual examples or evidence of why developers choose one vendor. AYA should demonstrate a missing workflow with a working port, not rely on an unsupported claim that a competitor's documentation is bad.
